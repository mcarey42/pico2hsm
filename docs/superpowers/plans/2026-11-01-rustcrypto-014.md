# RustCrypto 0.14 ECC Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move all firmware ECC (and `pico2hsm-tool`'s p256) from RustCrypto 0.13 / `crypto-bigint` 0.5.5 to 0.14 / `crypto-bigint` ≥ 0.7.6, which clears RUSTSEC-2026-0387. Behaviour and stored data stay byte-for-byte identical.

**Architecture:** First freeze today's ECC behaviour in known-answer tests, captured on 0.13. Then bump only the ECC crates. The new `rand_core` 0.10 / `digest` 0.11 generation lives beside the old one, and a single adapter lets the existing 0.6 RNGs feed 0.14. The firmware's public crypto signatures do not change, so callers are untouched. Hardware proves that a store written by the old firmware keeps working.

**Tech Stack:** Rust no_std on RP2350 (thumbv8m.main-none-eabihf), RustCrypto `p256`/`p384`/`p521`/`k256` 0.14.0, `elliptic-curve` 0.14.3, `ecdsa` 0.17.0, pytest hardware suite.

**Spec:** `docs/superpowers/specs/2026-11-01-rustcrypto-014-design.md`

## Global Constraints

- No `crypto-bigint` < 0.7.6 in any firmware build; `cargo audit` must not report RUSTSEC-2026-0387.
- Keys, DKEK, domain records and certificates stored by 2.1.x load and work unchanged. No keystore format change, no re-INITIALIZE.
- CVCs, signatures, ECDH results and status words are unchanged on the wire.
- Out of scope: `rsa` (stays 0.9), `ed25519-dalek`/`x25519-dalek` (stay 2), `sha2`/`hmac`/`hkdf`/`pbkdf2`/`aes-gcm` (stay on their current versions for non-ECC use).
- One RNG: no new entropy path. The 0.6 hardware RNG (`FwRng`) is the only source.
- Exact versions: `p256`/`p384`/`p521`/`k256` 0.14.0, `elliptic-curve` 0.14.3, `ecdsa` 0.17.0 (feature `algorithm` replaces `hazmat`), `crypto-bigint` resolved ≥ 0.7.6 (0.7.10 today).
- Build commands always pass `--no-default-features --features <board>,...` (CLAUDE.md). Host tests use `--target x86_64-unknown-linux-gnu`.
- Commit trailers: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_01SzmX3zRZNebJV2TRCpWhYS`.
- Hardware rules:
  - Only the dev boards are flashed during development: Pico 2 `DCD7948F6983C9CF` (probe `E664A836A3718537`) and peer `24984B5418676817` (probe `44EF2FABF14D8741`).
  - Production boards `139E6D9547578EEE` and `10ECEA541D6808A9` are touched only in Task 6.
  - Never flash `2e8a:10fd` boards, never write OTP, and stop probe-rs by PID, never `pkill -f`.

## Review Focus

1. **Short and over-length hashes** (MD5 16 B, SHA-1 20 B, SHA-512 64 B on P-256; 20 B on P-521) must sign and verify exactly as before; `bits2field` padding and truncation are the likely place for a silent change. Pinned in Task 1 (`ecc_kat::hash_lengths_are_unchanged`).
2. **Invalid ECDH peer points** (wrong length, off-curve, identity, compressed where it was refused before) must be refused exactly as before. Pinned in Task 1 (`ecc_kat::bad_peer_points_are_refused`).
3. **Out-of-range private scalars** (all-zero, ≥ n, wrong length) must give the same `CryptoError` as before; 0.14 changed `SecretKey`/`NonZeroScalar` constructors. Pinned in Task 1 (`ecc_kat::bad_private_scalars_are_refused`).
4. **Malformed or high-S signatures** passed to `ecdsa_verify` must return the same `Ok(false)` / `Err` split as before. Pinned in Task 1 (`ecc_kat::bad_signatures_verify_as_before`).
5. **A device store written by 2.1.x firmware** must sign with the same keys after the update. Pinned in Task 4, Steps 1 and 4.

- [ ] **Step 1: Write the vectors as tests with placeholder expectations.** Use one fixed private scalar per curve (P-256, P-384, P-521, K-256), written as hex literals of the full field length. Use fixed hashes, for example `[0x11; 32]` and `[0x22; 48]`. Tests:
  - `public_points_are_unchanged`: the public point is derived from each fixed scalar. Use `generate_ec_keypair` with a fixed-output test RNG (the `CounterRng` pattern in `protocol/sc_hsm/commands/pso.rs` tests) and record both the private key and the public point it gives.

    - `ecdsa_sign` output (DER) for P-256, P-384 and K-256 over a 32-byte hash;
    - `ecdsa_sign_p521_with_ad` over a 64-byte hash, once with `ad = &[]` and once with `ad = &[0x5A; 32]`;
    - each signature checked with `ecdsa_verify` → `Ok(true)`.
  - `ecdh_is_unchanged`: `ecdh_agree(A_priv, B_pub)` equals the recorded value and equals `ecdh_agree(B_priv, A_pub)`, per curve. Also `dkek::p256_ecdh` on the P-256 pair.
  - `domain_key_is_unchanged`: `domain_id(&q)` for the fixed P-256 point, and `verify_prehash` on a recorded (digest, signature) → `true`.
  - `hd_derivation_is_unchanged`: `bip32_derive` / `slip10_derive` (Secp256k1 and Nist256p1) from a fixed 64-byte seed on path `[0x8000002C, 0x80000000, 0, 1]`, recording the private key and the public key.
  - `hash_lengths_are_unchanged` (Review Focus 1): signatures over 16-, 20- and 64-byte hashes on P-256, and over a 20-byte hash on P-521 (`ad = &[]`).
  - `bad_peer_points_are_refused` (Review Focus 2): for each curve, `ecdh_agree` with a truncated point, `0x04 || zeros`, a point with Y+1, and the compressed form of a valid point. Record whatever today returns for each (`Err(..)` variant or `Ok`).
  - `bad_private_scalars_are_refused` (Review Focus 3): `ecdsa_sign` with an all-zero scalar, the curve order n, n+1 and a one-byte-short scalar, recording today's result.
  - `bad_signatures_verify_as_before` (Review Focus 4): `ecdsa_verify` with a DER signature truncated by one byte, one with s replaced by n−s (high-S), and one with r = 0, recording today's `Ok(bool)` / `Err`.

### Task 2: Port the firmware to RustCrypto 0.14

**Files:**
- Modify: `firmware/Cargo.toml` (ECC deps, plus a renamed `rand_core` 0.10 dependency), `Cargo.lock`.
- Create: `firmware/src/crypto/rng_compat.rs`.
- Modify the ECC call sites:
  - `firmware/src/crypto/asymmetric.rs`, `crypto/kdf.rs`, `crypto/mod.rs`;
  - `security/dkek.rs`, `security/key_blob.rs`;
  - `domain/key.rs`, `domain/member.rs`;
  - `protocol/sc_hsm/mod.rs`, `protocol/sc_hsm/commands/extras.rs`;
  - ECC uses in tests (for example `protocol/sc_hsm/domain_tests.rs`).
- Don't touch: `firmware/src/crypto/ecc_kat.rs` expected values.

**Interfaces:**
- Consumes: Task 1's `ecc_kat`.
- Produces:
  - `crate::crypto::rng_compat::Compat<'a, R>`, a wrapper `pub struct Compat<'a, R>(pub &'a mut R)`. For any `R: rand_core::RngCore + rand_core::CryptoRng` (0.6), it implements the `rand_core` 0.10 crypto-RNG traits that `elliptic-curve` 0.14 asks for, by delegating to the inner 0.6 RNG.
  - Every existing public crypto function keeps its exact signature, including its 0.6 RNG bounds, and wraps its RNG in `Compat` internally.

- [ ] **Step 1: Bump the dependencies.**
  - In `firmware/Cargo.toml` set `p256`/`p384`/`p521`/`k256` to `"0.14"` (same features), `elliptic-curve` to `"0.14"` (same features), and `ecdsa` to `{ version = "0.17", default-features = false, features = ["algorithm", "der"] }`.
  - Add `rand_core_010 = { package = "rand_core", version = "0.10", default-features = false }`.
  - Keep `rand_core` 0.6, `sha2` 0.10 and the rest as they are.
  - Run `cargo update -p p256 -p p384 -p p521 -p k256 -p elliptic-curve -p ecdsa`.
  - Then `cargo tree -p pico2hsm-firmware --target thumbv8m.main-none-eabihf --no-default-features --features pico2_4m,rsa,applet-piv,applet-openpgp-curve25519 -i crypto-bigint` must show only 0.7.x, ≥ 0.7.6.
