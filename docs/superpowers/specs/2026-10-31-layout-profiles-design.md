# Layout profiles: one definition for every board's flash map

Status: design, approved in conversation 2026-10-31 (issue #24, step 1).
Scope: the RP2350 boards that exist today. No new capacity, no new platform.

## 1. Why

Every board's internal-flash map is written down in at least six places
that must agree by hand:

| Where | What it holds |
|---|---|
| `firmware/src/storage/flash_layout.rs` | `MAP_4M` / `MAP_16M`, region offsets (`store_base + 0x8000`, …), `FLASH_16M` board list, compile-time asserts |
| `boards/*.x` (6 files) | linker `MEMORY` regions; identical per capacity except comments |
| `boards/pt_{4m,16m}[_prod].json` (4 files) | picotool partition tables (dev and production) |
| `build-all.sh`, `build-all-debug.sh`, `.github/workflows/build.yml`, `release.yml` | `case pico2_4m\|rp2350_one_4m) SIZE=4m` board→table mapping |
| `tests/hw/test_22_layout.py` | `STORE_4M` / `STORE_16M` sector ranges |
| `firmware/src/protocol/sc_hsm/mod.rs` | `MAX_SC_HSM_KEYS` (128/251) and `MAX_KEY_INDEX` (400/768) chosen by `FLASH_16M` |

A host test (`flash_layout::tests`) cross-checks the first three; the rest
are unchecked. Adding a board, or changing one region, means editing all of
them, and a miss shows up as a link error at best and a production board
with a partition table that can no longer be replaced at worst (the
production tables are read-only to BOOTSEL, FLASH_LAYOUT_2_0 §5.4).

The owner's goal: **consistency and less fragility on the boards we have
now.** A 2 MiB profile and other platforms come later; this work should
make them a small addition, not build them.

## 2. Goals

1. **One definition** of each capacity profile (regions, sizes, order,
   slots, permissions) and of the board → profile mapping.
2. **Everything else derived from it or checked against it:**
   - the linker `memory.x`, generated by `firmware/build.rs` (the six
     `boards/*.x` files are deleted);
   - the partition-table JSONs, generated by a small tool and committed,
     with a check that the committed files equal the generated ones;
   - the board → profile mapping used by the shell scripts and CI;
   - the region table used by the hardware layout test;
   - the firmware's `flash_layout` constants (kept by name, so the rest
     of the firmware does not change).
3. **The SC-HSM key cap computed from the keystore's size**, with an
   optional build-time override that cannot exceed the computed bound;
   the key index sized from the cap.
4. **CI enforces each board's image budget** (loadable image against its
   slot) and reports headroom.
5. **A "pure HSM" build** (SC-HSM only: no PIV, no OpenPGP) is built and
   host-tested in CI and passes the hardware suite once on a Pico 2.

## 3. Non-goals

- A 2 MiB (RP2354) profile, or any new capacity.
- The platform interface, security-capability states, or explicit
  platform selection (issue #24 step 2 and later).
- ESP32 or any other port (researched separately).
- Any change to the Storage V2 format, OTP layout, or provisioning.

## 4. Anti-goals (a failure even if it works)

- **Any change to an existing board's flash map.** Every region, every
  partition-table byte and every linker region must come out identical to
  today's. The two production boards (RP2350-One 139E6D…, LCD 10ECEA…)
  hold signed production tables that BOOTSEL cannot replace, and their
  keystores must still open after a firmware update.
- A build that silently falls back to a default board or profile (today
  `build.rs` falls back to `rp2350_one_4m`).
- A generator that needs network access or a non-Rust toolchain.

## 5. Constraints

- Firmware is `no_std`; the definition must be usable in `const` context
  (the firmware's compile-time asserts and `heapless` capacities depend on
  it).
- `build.rs` runs on the host for every build; it may depend on a
  workspace crate as a build-dependency.
- picotool consumes the partition-table JSON (`picotool partition create`),
  including the signing step for production tables; the JSON format and
  field order must stay picotool-compatible. The committed JSONs remain
  the reviewable source for signed production tables.
- Existing feature names, script interfaces (`build-all-debug.sh <board>`)
  and CI job names stay.
- Host tests run with `--target x86_64-unknown-linux-gnu` (see CI).

## 6. Design (decided)

### 6.1 A `pico2hsm-layout` crate

A new workspace member, `no_std` by default, with a `std` feature for the
generators. It holds data and `const fn`s only:

- `SECTOR`, `PT_SIZE`, and a `Profile` type: flash size, slot count and
  size, slot start addresses, the ordered list of store regions (name,
  size, partition name, bootloader permission), keystore start/end.
- `PROFILE_4M` and `PROFILE_16M`, whose values reproduce today's
  `MAP_4M` / `MAP_16M` exactly, including the offsets now written as
  `store_base + 0x8000` etc. (derived from region sizes in order).
- `BOARDS`: board feature name → profile, one row per board
  (`pico2_4m`, `rp2350_one_4m`, `rp2350_one_16m`, `rp2350_geek_16m`,
  `rp2350_geek_sdcard`, `waveshare_rp2350_lcd_16m`,
  `waveshare_rp2350_lcd_sdcard`).
- `const fn` validation, run as `const _: () = assert!(…)` for every
  profile: sector alignment, ordering and disjointness, inside the flash,
  rotation minimums (≥ 2 sectors for rotated logs), the MIDPOINT_RULE (no
  bootloader-closed region contains `flash_size / 2`), and the RP2350-E10
  tail sector kept out of every partition on 16 MB. These move from
  `flash_layout.rs`; none is dropped.
- The key-cap computation (6.4).

With `std`: functions rendering a profile as `memory.x` text and as a
picotool partition-table JSON (dev or production permissions).

### 6.2 Generated `memory.x`

`firmware/build.rs` maps the active board feature to its `BOARDS` row.
`rp2350_one_16m` keeps implying `rp2350_one_4m` (feature graph unchanged);
`BOARDS` gives each row a precedence so that pair resolves to
`rp2350_one_16m`, and any other combination of two or more boards, or
none, fails the build with a message naming the active board features.
This holds for every target, host included: the firmware's host tests
already pass a board feature in CI, and `flash_layout` and the key cap
now come from the board's profile on the host too. (Today's silent
fallback to `rp2350_one_4m` is removed.) `pico2hsm-core` and the
integration-test crate do not depend on board features and are
unaffected and writes `memory.x` to `$OUT_DIR` from the profile. The
`BOOT2`/`.start_block` section and `RAM` region (identical on every board
today) are emitted by the same renderer. The six `boards/*.x` files are
deleted. A host test renders every board's `memory.x` and compares the
regions with the values the deleted files had (kept as a golden table in
the test), so the change provably changes nothing.

### 6.3 Generated, committed partition tables

A binary in the layout crate (`cargo run -p pico2hsm-layout -- …`, `std`
feature) offers:

- `pt <profile> [--prod]` — print the JSON;
- `write` — regenerate `boards/pt_*.json`;
- `check` — exit non-zero if any committed `boards/pt_*.json` differs from
  its generated form (byte for byte);
- `profile <board>` — print the profile name (`4m` / `16m`) for scripts;
- `regions <board>` — print the store regions (name, start, size) for the
  hardware test.

CI runs `check` in the lint job. The generated JSONs must be byte-identical
to today's committed files (the first `write` must produce an empty diff;
if picotool-irrelevant formatting differs, match today's formatting rather
than reformatting the committed files).

### 6.4 Computed key cap

`MAX_SC_HSM_KEYS` becomes the smaller of 251 (every user key ref below the
reserved 0xFC) and a bound computed from the keystore partition size and
the store engine's geometry (NOR media): data sectors after the 16-sector
journal ring, less the snapshot sectors needed for the maximum live index
(two chains during a checkpoint), less the maintenance reserve the engine
needs to replace an object and complete a checkpoint, less a fixed budget
for PIV, OpenPGP, reserved SC-HSM records (0xFC–0xFF) and domain records,
divided by three objects per key (key, descriptor, certificate).

SD-card boards (`rp2350_geek_sdcard`, `waveshare_rp2350_lcd_sdcard`) keep
their keystore on the card, whose size is known only at runtime; their
internal keystore partition is unused. Their cap is pinned at 251, with a
compile-time assert that a card holding the engine's maximum data range
(`MAX_DATA_SECTORS`, SD geometry) fits 251 keys under the same formula. A
card too small for its keys already fails a save with KeystoreFull
(6A84); no new runtime check.
`MAX_KEY_INDEX` is derived from the cap with the same formula the current
assert uses (`cap * 3 + 4`) plus the existing allowance for free-standing
files.

A build may lower the cap with `PICO2HSM_MAX_SC_HSM_KEYS=<n>`
(`build.rs` passes it through; a value above the computed bound or below 1
fails the build with the bound in the message).

The engine constants the computation needs (ring size, snapshot entries
per sector, slot/sector reserves) must come from the store engine's own
definitions, not copies: move or re-export them so the layout crate and
`store_v2` share one value, or have `store_v2` assert equality.

### 6.5 Scripts, CI and the hardware test use the definition

- `build-all.sh`, `build-all-debug.sh`, `build.yml`, `release.yml`: the
  `case … SIZE=4m` statements are replaced by
  `pico2hsm-layout profile <board>`.
- `tests/hw/test_22_layout.py`: `STORE_4M`/`STORE_16M` are replaced by the
  regions read from `pico2hsm-layout regions <board>` (or the committed
  JSON for the board's profile); it still compares them with the table the
  device reports (`80 FE 16`).
- `firmware/src/storage/flash_layout.rs` keeps its public constant names
  (`MAP`, `FIRMWARE_END`, `BINDING_OFFSET`, `RETRY_COUNTER_OFFSET`,
  `RSA_POOL_OFFSET`, `LEGACY_COUNTER_OFFSET`, `QMI_KEYSTORE_*`,
  `FLASH_16M`, …) as re-exports computed from the board's profile, so no
  caller changes.

### 6.6 Image budget in CI

For each board in the build matrix, after the release build, CI converts
the ELF to its loadable binary and fails if it exceeds the slot size from
the profile; it prints size, slot and headroom (bytes and %). (The linker
already refuses an image that overflows the FLASH region; this check
covers the loadable image as flashed and makes the headroom visible.)

### 6.7 Pure HSM build

- CI: add an SC-HSM-only feature set (`<board>,rsa` without the applet
  features) for one 4 MB board (`pico2_4m`) and one 16 MB board
  (`waveshare_rp2350_lcd_16m`): build and host tests.
- Hardware: one full suite run on a development Pico 2 with that build.
  PIV/OpenPGP tests must skip cleanly when the applet is absent; fix any
  that fail instead of skipping.

## 7. Verification

- Host: the layout crate's tests; golden comparisons for `memory.x` and
  the partition JSONs; existing firmware host tests on every board; the
  key-cap test (`the_sc_hsm_key_cap_counts_keys_not_files` and a fill-to-
  cap test on a keystore of exactly the profile's size).
- Hardware, development Pico 2 (probe E664A836A3718537, reader
  DCD7948F6983C9CF): flash the new firmware over the existing store
  without formatting; the keystore must open with its keys; full suite.
  Then the pure-HSM run.
- Hardware, production boards: after the development-board checks pass,
  this work ships as release **2.1.0** (the key cap is a user-visible
  change; release notes say so). The implementer signs the CI-built 2.1.0
  release image with `ec_firmware_signing_key-bootkey0.pem`, as for
  2.0.1, and installs it on the RP2350-One and the LCD board; the owner
  presses BOOT when asked. 2.1.0 is above the installed 2.0.1, so the
  bootrom prefers it. Checks: `picotool partition info` unchanged; the
  keystore opens with its keys; the release-build suite passes.

## 8. Left to the builder

- Exact module/type names inside the layout crate.
- Whether the CLI is a `[[bin]]` in the layout crate or a separate tools
  crate.
- The PIV/OpenPGP/domain object budget numbers in 6.4 (derive them from
  the applets' maximum object counts; document each).
- How the CI image-budget step obtains the binary (objcopy or picotool).

## 9. Calls made by the designer (not asked of the owner)

- The key-cap override is a build-time environment variable, not a
  runtime/provisioning setting.
- Partition-table JSONs stay committed (generated + checked), rather than
  generated at build time, because the signed production tables are made
  from them and should be reviewable in git.
- The linker scripts are generated at build time and deleted from git.
- The computed cap may come out different from 128 on 4 MB boards (it
  reflects what the keystore actually holds); no devices depend on 128.
- The work ships as release 2.1.0, and the implementer signs and installs
  it on the production boards (owner presses BOOT).
- SD-card boards keep a pinned cap of 251, checked against the engine's
  maximum SD data range at compile time.
- `rp2350_one_16m` keeps implying `rp2350_one_4m`; a precedence resolves
  the pair; every other multi-board or no-board build fails, on every
  target.
